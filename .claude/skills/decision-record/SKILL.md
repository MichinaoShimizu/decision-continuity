# decision-record

組織の誰かが決めたことと、「誰が決める・承認するか」という決め方を、あとから探せる形で残す。記録（DR）は記録のリポジトリ（このリポジトリ。ほかのリポジトリからはこのフォルダーの `STORE` に書いたもの）の `records/` に、1 件 1 ファイルの Markdown で置く。答えはユーザーの言葉で返す。

コードのリポジトリでは、ADR キット（`adr/`）の `adr-guard` がこの記録を読んで変更を確かめ、`reverse-adr` が過去の変更を Decision logs に起こす。

## モード

渡されたものと頼まれ方から選ぶ。使う人にモード名を覚えさせない。

| モード | こんなとき | 返すもの |
|---|---|---|
| 聞く | 「なんでこうなってる？」「誰の承認で決まる？」「これ自分で決めていい？」 | 記録だけを根拠にした答えと、使った DR 番号。なければ「記録なし」と、誰に聞けばよさそうか |
| 拾う | スレッド・議事録・PR・決めた人の返事を渡された | DR の下書き（`entry: auto`、元になかった項目つき） |
| 書く | これから重い判断を決めたい。設計の判断を残したい | 問いかけと、提案中の DR |
| 決め直す | 過去の DR を変えたい | 新しい DR と、古い DR への「終了」の追記 |
| 決定にする | Decision log の変更を、決定として残したい | 新しい DR と、Decision log への一行の追記 |
| 追記する | 見直しの時期が来た、結果が出た、提案中の DR が決まった、探し方を直したい | 古い DR への一行の追記 |

「聞く」で記録がなければ、決めた人に聞いて、その返事を「拾う」に回すよう勧める。必要とされたときに残すので、使われる決定だけがたまる。

## 拾う

1. 決定だけを抜き出す。雑談、ブレインストーミング、検討中の話、AI が出しただけの案は決定にしない。迷ったら「これは決定ですか？」と聞く。
2. 決めた人は名前ではなく役割（`config.yaml` の roles）と組織で書く。最終的に決めた役割を `decided_by` に（複数で決めたなら全員）、決める前に承認した役割を `approved_by` に承認した順で入れる。任された人が決めたときは、決まった種類の判断をずっと任せているなら委譲の決め方の記録を `approved_via` に入れ、この件だけ任されたなら `decided_by` のその人に `delegated_by`（任せた役割）を添える。元に名前しかなければ役割に置き換え、分からなければ `unconfirmed` に入れる。人の異動や退職があっても記録が古くならないようにするため。決めた日と元の場所も埋める。貼られた文章や本人の発言も元の場所として扱い、URL がなければ `unconfirmed` に入れる。
3. 状態は元の場所の事実から写す。承認、マージ、「決めた」「入れた」などの報告があれば `accepted`。「〜しよう」「〜する予定」だけなら `proposed`。
4. 「誰が決める・承認するか」を定めたものは `kind: flow`。決定がどの決め方を通ったか分かれば `approved_via` にその番号を入れる。
5. 元に書かれていないことは埋めない。項目のキーを `unconfirmed` に入れる。
6. 拾ったものは `entry: auto`。本人の確認は待たない。人が会話で伝えてきた決定は `entry: explicit`、元の場所は `manual`。
7. PR のマージは「変更が入った」証拠で、「方針として決めた」証拠ではない。PR から拾うのは、PR やレビューに決定の言葉（「〜にする」「〜と決めた」）と決めた人がいるときだけ。変更しか分からないものは DR にせず、`reverse-adr` の Decision log にする。決め方（`kind: flow`）が求める承認が元の場所に見えなくても、拾うことはやめない。見えない承認は `approved_by` を `unconfirmed` に入れ、「#番号 の決め方の承認が見えない」と添える。決め方を守ったかどうかは人が判断する。
8. コードに関係する決定なら、`repos`・`paths`・`keywords` を元に書かれている範囲で埋める（下の「探し方」）。

## 入り方

- `explicit`：人が意図して追加した。そのまま根拠にしてよい。
- `auto`：仕組みや AI が拾った。元の場所と一緒に「拾った内容」として扱う。
- 人が `auto` の記録を直すか採用すると `explicit` に変わる。自分の判断では変えない。

## 書く

一つずつ聞き、答えを提案中の DR にまとめる。答えられない問いは未定のまま残し、責めない。答えのない項目は本文に「未記入」と書き、推測で埋めない（推測は「案」と断っても本文に入れない。問いの側に「たとえば〜ですか？」と書く）。

1. 何を決めたいか。一文で言うと？
2. なぜ今か。前提にしていることは？（崩れたら見直す前提になる）
3. 他の案は？ 何もしないとどうなる？
4. 得るものと、後回しになるものは？
5. 誰に影響し、どの決め方で合意を取るか？
6. 戻せるか。外れたときのリスクを誰が引き受けるか？
7. どうなったら決め直すか。いつ、何で分かるか？
8. 反対意見と、その理由は？
9. （コードに関係する決定なら）どのリポジトリの、どんな変更がこの決定に触れそうか。触れそうなパスと、変更に出てきそうな名前（関数・設定・テーブルなど）は？ 守れているかをどう確かめるか（テスト、監視）？

## 重さ

重さは保存しない。`scope`・`reversibility`・`touches_sensitive` から毎回決め、`rationale` に書く深さだけを変える。

| 重さ | 条件 | `rationale` に書くこと |
|---|---|---|
| 軽い | チーム内で、すぐ戻せる | なぜ（一行） |
| 標準 | 複数チーム、または戻すのに手間 | ＋他の案、後回しになるもの、前提 |
| 重い | 部署横断・全社、または戻せない | ＋使った決め方、反対意見、リスクを引き受けた人 |

セキュリティ・個人情報・権限・監視や通知・ログに触れる決定は、範囲が小さくても一段重く扱う。戻しても漏えいや検知漏れは取り返せないため。迷ったら重いほうに寄せ、理由を一行添える。重さに対して足りない項目は、決めた人に一度まとめて聞く。保存は止めない。

## 聞く

記録だけを根拠に答え、使った DR 番号を必ず示す。「誰の承認で決まる？」には `kind: flow` を優先して使う。「これ自分で決めていい？」には、似た領域・影響範囲の判断を過去にどの役割が決め（`decided_by`）、どの役割が承認してきたか（`approved_by`）を示し、最後の判断は本人と組織長に委ねる。`auto` の記録を使うときは「拾った記録では」と添え、崩れた前提がある記録は「見直しが必要」と添える。記録がなければ、`config.yaml` の roles か担当チームから聞く相手を挙げ、分からなければ質問者に「この領域の持ち主は誰か」を聞く。

## 状態

状態は3つだけ。縛るのは「有効」だけ。

| 状態 | 表し方 |
|---|---|
| 提案中 | 「終了」の追記がなく、`status: proposed`（「決まった」の追記がない） |
| 有効 | 「終了」の追記がなく、`status: accepted`、または「決まった」の追記がある |
| 終了 | 「**終了**」の追記がある。置き換えたなら一行目に「置き換え」、やめたなら理由 |

Decision logs の記録には状態がない。過去の観察で、何も縛らない。

## 探し方（repos・paths・keywords）

コードのリポジトリの `adr-guard` が、変更に関係する決定を見つけるための項目。決定の中身ではない。

- `repos`：縛るコードのリポジトリ名。どのリポジトリにもかかわる決定（例：個人情報をログに出さない）は `[all]`。コードに関係しなければ空。
- `paths`：関係するパス。前方一致で当てる。
- `keywords`：**決定の文に出てこないのに、変更の側に出てくる言葉**。差分にそのまま当たるコードの識別子（`logger`、`MAX_RETRIES`、テーブル名、環境変数）と、言い換え（ログ・トレース・監視）。決定の文にある言葉は入れなくてよい。
- 三つとも一行の `[a, b]` で書く（読むスクリプトが一行で読む）。分からなければ空のままにする。空でも `adr-guard` はタイトルと決定の文を意味で照らす。

## 追記と決め直し

記録は追記だけで育てる。本文はマージしたあと書き換えない。結果も崩れた前提も、末尾に追記する（例：「**前提が崩れた**（YYYY-MM-DD）：組織長が承認の判断を期限内に返せる → 3週間返らない例が続いた」）。

追記の一行目を次の印で始めると、記録データ（フロントマター）に重ねて読まれる。それ以外の追記は状態を変えない。本文の `status: proposed` は、決まったあともそのまま残る（本文は書き換えない）。直す必要はない。

- **決まった**：提案中の DR が決まったとき。「**決まった**（YYYY-MM-DD）：決めた人（役割）、承認した人、元の場所」。元の場所に承認の事実がないなら書かない。
- **探し方を更新**：パスが変わった、キーワードが足りなかった、`repos` や `paths` が空で拾えなかったとき。`repos`・`paths`・`keywords` のうち変える項目だけを、**最新の一覧まるごと**で書く。空だった項目もこれで足せる。記録を立て直す必要はない。

  ```
  **探し方を更新**（2026-11-02）
  paths: [src/observability/]
  keywords: [logger, audit_log, Sentry]
  ```

決め直すときは新しい DR を作り、本文に「#番号 を置き換える」と書く。古い DR には「**終了**（YYYY-MM-DD）：#新しい番号 に置き換え」と追記する。新しい DR と同じ PR に入れてよい。

## Decision log から決定にする

Decision log はずっと Decision log のまま。書き換えも終了もしない。決定にするときは、新しい DR を作る。

- **当時の理由と決めた人が分かった**（Q&A の答え、決めた本人の話）：「拾う」で DR にする。状態と決めた日は、答えに書かれたとおり。Q&A なら `sources` に `asked` で入れる。
- **理由は分からないが、いまの形をこれからのルールにしたい**：「書く」で提案中の DR を作り、決め方の DR に沿って承認されたら「決まった」の追記で有効にする。決めた日はその日。Decision log の日付にさかのぼらせない（当時決めたことにすると作り話になる）。
- どちらでも、DR の本文に「#（Decision log の番号）の観察にもとづく」と書き、Decision log には「**決定になった**（YYYY-MM-DD）：#（DR の番号）」と追記する。
- マージされた、時間がたった、adr-guard がよく参照する、エージェントがそう判断した、のどれも決定の理由にならない。決めるのは決め方の DR が定める役割。

## 守ること

- 状態は元の事実を写すだけ。自分の判断で `accepted` や `explicit` にしない。
- 「記録しないで」と言われたものは、下書きも残さない。
- 人事（評価・異動・処遇・個人の情報）に関わる判断は取り込まない。「限定の場所に手で残してください」と伝える。DM は本人が渡したときだけ扱う。
- 記録を個人の評価やランキングに使わない。外れたときは、人ではなく決め方と前提を振り返る。
- 中身の良し悪しは判断しない。問いを投げるだけ。

## 置き場所（records/ の Markdown）

記録は記録のリポジトリの `records/` に、1 件 1 ファイルの Markdown で置く。変更は PR で入れ、既定のブランチにマージされたら保存されたことになる。

| 種類 | フォルダー |
|---|---|
| 決めたこと | `records/decisions/`（Decisions） |
| 決め方（kind: flow） | `records/decision-flows/`（Decision flows） |
| 過去に起きた変更の観察（縛らない） | `records/decision-logs/`（Decision logs。書式は `reverse-adr`） |
| 「なんで？」の質問 | `records/questions/`（Q&A） |

- **番号**：ファイル名の先頭の 4 桁（`0042.md`、`0042-no-pii-in-logs.md`）がそのまま DR 番号（例：#42）。番号はフォルダーをまたいだ通し番号で、`records.py create` が次の番号を振る。手で作るときも、いちばん大きい番号の次にする。
- **ファイル**：先頭に記録データ（YAML のフロントマター。`---` と `---` で挟む）、その下に `# タイトル`、本文、さらにその下に `---` と「追記」が続く。ファイルを消したり、名前やフォルダーを変えたりしない。
- **タイトル**：何を決めたかが分かる一行。
- **関係**：項目として持つのは `superseded_by`（置き換え）と `approved_via`（使った決め方）だけ。前提にしている決定や関連する決定は、本文に `#番号` を書く。逆向きのつながりは `records.py show` が「参照している記録」として出す。
- **本文**：人が読む文章。記録データはフロントマターに置き、本文には書かない。形は下の「本文の書き方」。
- **追記**：コメントにあたるもの。ファイルの末尾に `## 追記 YYYY-MM-DD（書いた人）` の見出しで足す（`records.py comment` が付ける）。前の行は変えない。
- **状態**：上の「状態」のとおり。終わらせるときは「**終了**」の追記を足す。置き換えたなら「**終了**（YYYY-MM-DD）：#番号 に置き換え」、やめたなら「**終了**（YYYY-MM-DD）：やめた。（理由）」。
- **Q&A**：答えが付いた質問は「拾う」に回し、新しい DR の `sources` に `asked` としてその Q&A を入れる。
- **読み方**：リポジトリのルートで `python3 .claude/skills/decision-record/records.py <コマンド>` を実行する（絶対パスにしない。許可の設定がこの形で書かれている）。`index --repo <名前>` で探すための一覧、`show <番号>` で本文と追記、`config` で記録のリポジトリの `config.yaml`。記録のリポジトリがほかのリポジトリ（`STORE` の `owner/repo`）なら、読むたびにキャッシュへ最新を取ってくる（`git` で読めること）。終了コード 2 は「読めなかった」で、「記録がない」ではない。
- **書き方**：記録のリポジトリの手元のクローンで、既定のブランチから新しいブランチを切り、`python3 .claude/skills/decision-record/records.py create --category <フォルダー名か種類の名前> --title <タイトル> --body-file <ファイル>`、追記は同じく `comment <番号> --body-file <ファイル>`。ファイルを作れないときは `--body-file -` にして本文を標準入力で渡す。ほかのリポジトリから書くときは `--store <クローンのパス>`（か環境変数 `DR_STORE`）を付ける。書いたら `records.py check --base origin/<既定のブランチ>` を通し、コミットして PR を出す。PR を出したら「PR を出した（マージで保存される）」と、番号とファイルと PR のリンクを伝える。マージ前に「保存した」と言わない。
- **番号がぶつかったとき**：ほかの PR が先に同じ番号でマージされたら、自分の側のファイルの番号を振り直す（`check` が知らせる）。マージ前のファイルなので書き換えてよい。
- **書けないとき**：記録のリポジトリに PR を出す手段がない環境では、タイトルと本文をそのまま貼れる形で返し、「まだ保存していません」と明記する。ほかのリポジトリに書いて代わりにしない。

### 本文の書き方

`--body-file` に渡すファイルは、先頭に記録データのフロントマター、その下に本文を書く。`records.py create` がフロントマターをファイルの先頭に、タイトルをその下に置く。本文は、読む人のために決めたことを一行目に置く。

````markdown
---
（下の「記録データの型」）
---

**（決めたこと：一文）**

| 決めた人 | 決済チームのチームリード |
|---|---|
| 承認 | セキュリティ責任者 |
| 使った決め方 | #12 |
| 影響範囲 | チーム内・すぐ戻せる |
| 決めた日 | 2026-10-03 |

**なぜ**
（理由。重い判断なら他の案、反対意見、リスクを引き受けた人も）

**前提（崩れたら見直す）**
- （前提）

**元の場所**：（リンク）
````

- 表の値は人が読む言葉で書く（`config.yaml` の roles の表示名、「部署横断・戻すのに手間」など）。分からない値は「不明」。
- 空の行（承認がない、決め方を使っていない）は省く。
- 拾った記録（`entry: auto`）は一行目の下に「> 拾った内容です。元の場所と合わせて読んでください。」と添える。

### 記録データの型

フロントマターの中身。トップレベルの `key: value` を 1 行ずつ書き、リストは 1 行の `[a, b]` で書く（`records.py` はこの形だけを読む）。前の形（本文の最後の ```` ```yaml ```` ブロック）も読めるが、新しく書くときはフロントマターにする。

```yaml
kind: decision            # decision | flow（誰が決める・承認するかの決め方）
status: accepted          # proposed | accepted（終了の追記の後は superseded | retired）
approved_via: null        # 通った決め方の DR 番号（例：#12）
superseded_by: null
entry: explicit           # explicit: 人が追加 | auto: 仕組みや AI が拾った
decided_at: null          # YYYY-MM-DD
decided_by: []            # 最終的に決めた役割 [{role, org, delegated_by?}]。複数なら全員で決めた。この件だけ任されたなら delegated_by: {role, org}
approved_by: []           # 決める前に承認した役割 [{role, org}]（承認した順）
domain: technology        # technology | product | organization | business
scope: team               # team | multi_team | cross_department | company
reversibility: easy       # easy | costly | irreversible
touches_sensitive: false  # セキュリティ・個人情報・権限・監視や通知・ログに触れる
repos: []                 # 縛るコードのリポジトリ名。全リポジトリなら [all]。コードに関係しなければ空
paths: []                 # 関係するパス（前方一致）
keywords: []              # 決定の文に出てこないのに変更に出てくる言葉（コードの識別子、言い換え）
decision: ""
premises: []              # [text] 崩れたら追記する
sources: []               # [{type, url}] type: chat|meeting|pr|ticket|approval|asked|manual
unconfirmed: []           # 元に書かれていなかった項目のキー
```

既存の ADR は `entry: explicit` で取り込める（Context→本文、Decision→`decision`、Status→状態、Consequences→後の追記、ADR 索引のパスとキーワード→`paths`・`keywords`、置き場所のリポジトリ→`repos`）。Accepted でない ADR は `status: proposed` で取り込む。
