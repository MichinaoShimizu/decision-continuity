# 判断を途切れさせない回し方

古いアプリケーションを AI が設計・実装・テストできるようにするには、過去の判断を掘り起こし、いまのコードにつなぎ、変えるたびに照合し、新しい判断を記録し続ける。

| 段 | いつ | 使うもの | できるもの |
|---|---|---|---|
| 1. 流れをつかむ | 最初に 1 回、その後は月に 1 回 | change-history | `docs/change-history/`：月ごとの全変更、主な変更、年表 |
| 2. 掘り起こす | 最初に、大事なテーマごと | decision-log の `audit`・`write` | `docs/decision-logs/`：なぜ（記録にある範囲で）、ステータス、分かっていないこと |
| 3. 現在につなぐ | 月に 1 回か、リリースの前 | `build_index.py --stale` と、頼まれたときの確かめ直し | ステータスが `Active`・`Superseded`・`Removed` のどれかに保たれる |
| 4. 照合する | 振る舞いを変える前（設計・実装・テスト） | decision-log の `check` | 守っている判断、食い違うおそれ、先に聞く問い、足すテスト |
| 5. 記録する | 判断が決まったとき | decision-log の `record` | 変更と同じ PR に入った Decision log |

4 と 5 を毎回回すには、対象のリポジトリの `CLAUDE.md`（Kiro は `.kiro/steering/`）に次を足す。

```markdown
## 判断の照合と記録

- 値・境界・方針など振る舞いを変える前に、decision-log の check で docs/decision-logs/ を照合する。
- Active の判断と食い違うときは、進める前に人に確かめる。理由が「不明」の判断は、知っていそうな人に聞く。
- 人が判断を決めたら、decision-log の record で、変更と同じ PR に記録を足す。
```

照合は `build_index.py <置き場所> --related <パス>… --words <言葉>` が、パスと言葉で機械的に当てる。当たらなかったのは「記録された判断がない」だけで、判断がなかったとは限らない。大事な場所なら 2 に戻って掘り起こす。

実在のリポジトリ（pallets/flask）での効果は [evals/legacy/README.md](../evals/legacy/README.md)。過去の判断と食い違う依頼を出したとき、仕組みがなければ AI は 2 回とも DoS 対策の既定を黙って外し、仕組みがあれば 2 回とも照合して止まり、人に確かめた。
