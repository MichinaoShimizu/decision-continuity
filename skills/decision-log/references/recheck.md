# 再確認（decision-log の `recheck`）

Decision log の状態（いまも同じ、など）は、書いたときの基準のコミットでの観察である。コードがその後に変わると、本文の状態は古くなる。本文は書き換えないので、確かめ直した結果は「再確認」の追記で足す。

## 手順

1. 古くなったものを挙げる。リポジトリのルートで、索引のスクリプトを相対パスで呼ぶ。
   `python3 .claude/skills/decision-log/scripts/build_index.py <置き場所> --stale`（Kiro なら `.kiro/skills/…`）
   - 「現在」のリンク（`/blob/<ハッシュ>/<パス>#L12`）の先が、確かめたコミット（いちばん新しい「再確認」の追記、なければフロントマターの `checked`、なければリンクのハッシュ）より後に変わったものを挙げる。行の範囲があれば、その範囲に当たる変更だけを数える。
   - 「確かめられない」は、そのコミットが手元にないとき。浅いクローンなら `git fetch --unshallow` をしてから回す。
2. 挙がった Decision log ごとに、C 行を基準のコミット（`HEAD`）で確かめる。`git show HEAD:<パス>`、`git grep -n <識別子> HEAD`、変えた変更は `git log --first-parent --format='%h %ad %s' --date=short-local <確かめたコミット>..HEAD -- <パス>` で探す。ファイルが変わっても、C 行の中身が同じなら「いまも同じ」のままにする。
3. 末尾に追記を足す。本文は書き換えない。

   ```markdown
   ## 追記 2026-01-20（書いた人、再確認）

   **再確認**（2026-01-20、def5678）
   **いま**：上限は 7。理由は分かっていない。

   - C1：いまも同じ → 置き換え済み。[PR #160][pr160] で 5 から 7 になった（322 日後）
   - C2 はいまも同じ（ファイルは変わったが、該当の行は同じ）

   [pr160]: <PR #160 の URL>
   ```

   - 変わったものに理由が書かれていれば、新しい Decision log にするかを [writing.md](writing.md#追記にするか新しい-decision-log-にするか) で決める。
4. 索引を作り直し、`--check` と `--stale` が通ることを確かめる（[save.md](save.md)）。

`recheck` は書くので、`write` と同じく頼まれたときだけ回す。`audit` では、手順 1 と 2 の結果を報告の「履歴のみ」の節に書き、追記は下書きで返す。
